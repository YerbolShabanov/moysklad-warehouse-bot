# Телеграм-бот складовщика · МойСклад

Бот по номеру заказа покупателя показывает кладовщику карточку заказа
из МойСклад вместе с **ячейками адресного хранения** по каждой позиции.

```
Заказ покупателя 1068634272          ← подпись к файлу
Статус: Выдан
Дата: 09.09.2026 10:09
Канал продаж: ОПТ
Позиций: 16

📎 Заказ-1068634272.xlsx             ← вложение, готово к печати
```

Внутри файла — таблица в порядке обхода склада:

| № | Наименование товара | Штрихкод | Кол-во | Ячейка |
|---|---|---|---|---|
| 1 | 331902 new, Складной коврик Soft Floor (watercolor) | 4690624101267 | 3 | Р2-М12-Э1 |
| 2 | Ходунки "SMILEY V2" (grey) | 4690624101601 | 2 | Р2-М13-Э1 |
| 3 | Автокресло OXIS (sand) | 4690624238147 | 1 | Р3-М4-Э3 |

* **Формат** задаётся `ORDER_FORMAT`: `xlsx` (по умолчанию — файл для
  печати), `text` (таблица прямо в сообщении) или `image` (PNG).
* **Штрихкод** — первый из карточки товара (`barcodes[0]`), а не артикул.
  В xlsx хранится текстом, иначе Excel срезал бы ведущие нули.
* **Ячейка** — одна на товар. Сначала отсекаются ячейки, где товара
  **не хватает на всё количество позиции**: нет смысла гнать сборщика
  туда, где придётся добирать из второго места. Среди достаточных
  действует приоритет этажей — **снизу вверх**: первый этаж, иначе
  второй, иначе третий и выше.
  На верхних этажах лежат упакованные паллеты — их снимают погрузчиком,
  поэтому туда идём в последнюю очередь. Внутри одного этажа берём ячейку
  с большим остатком: больше шансов закрыть количество из одной точки.
  Напольные ячейки без этажа («Приёмка», «Комплектация стол») идут между
  вторым и третьим этажом — брать с них проще, чем гонять погрузчик.
  Если достаточной ячейки нет нигде, берётся лучшая по тем же правилам,
  а в колонке «Ячейка» дописывается фактический остаток —
  `Р1-М1-Э1 (есть 1 из 10)`, чтобы сборщик узнал о нехватке до похода
  к стеллажу, а не у него.
* **№** — порядок сборки, а не номер позиции в заказе: строки уже
  отсортированы по маршруту, поэтому нумерация идёт подряд. В текстовом
  режиме колонки `№` нет — там на счету каждый символ ширины.
* **Порядок строк** — обход склада: по ряду, месту и этажу (числами, а не
  по алфавиту: `Р10-М3` раньше `Р10-М9`). Нестандартные ячейки
  («Приёмка», «Комплектация стол») — в конце, за ними позиции без ячейки.
* Имена ячеек сокращаются: «Ряд 10 место 9 этаж 2» → «Р10-М9-Э2»
  (`COMPACT_SLOT_NAMES=false` — полные).
* Лист настроен на печать: A4, подгон по ширине, шапка таблицы
  повторяется на каждой странице, включены фильтры и закрепление строк.
* В режиме `text` таблица укладывается в `TABLE_WIDTH` символов
  (по умолчанию 58): Telegram **переносит** длинные строки, а не
  прокручивает, поэтому колонка с названием берёт остаток ширины и
  режется **по середине** — у товаров вида «артикул, товар (цвет, размер)»
  отличительная часть стоит в конце, обрезать хвост нельзя.

## Команды

| Команда | Действие |
|---|---|
| `00123` (просто текстом) | карточка заказа по точному номеру |
| `/order 00123` | то же самое явной командой |
| `/find Ромашка` | поиск заказа по номеру или контрагенту, выбор кнопкой |
| `/refresh` | сбросить кэш склада и ячеек |
| `/chatid` | показать id чата — нужен для настройки оповещений |
| `/help` | справка |

## Установка

```bash
cd ~/Documents/moysklad-warehouse-bot
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env`:

* `TELEGRAM_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
* `MOYSKLAD_TOKEN` — МойСклад → *Настройки → Профиль → Токен доступа к API*.
  Токен передаётся как `Authorization: Bearer <token>`.
* `MOYSKLAD_STORE_NAME` — по умолчанию `Склад адрес. хранение`, менять не нужно.
* `ALLOWED_USER_IDS` — Telegram user_id тех, кому бот отвечает в личке.
  Если доступ держится составом группы, оставьте пустым и задайте
  `NOTIFY_CHAT_ID` — см. раздел про оповещения.

Запуск:

```bash
./.venv/bin/python main.py
```

При старте бот проверяет доступ к API и пишет в лог найденный склад и
количество ячеек — если склад не найден, будет явная ошибка в логе.

## Куда уходит какой заказ

Заказы разводятся по трём маршрутам — см. [msbot/routing.py](msbot/routing.py):

| Заказ | Что происходит |
|---|---|
| Kaspi **без** галочки «Экспресс доставка» | копится в **сводный сборочный лист** — один файл на несколько заказов |
| Kaspi **с** галочкой | уходит сразу отдельным сообщением с пометкой ⚡️ ЭКСПРЕСС |
| **ОПТ** | отдельным сообщением, но **только** в статусе из `OPT_STATES` |
| Остальные каналы | отдельным сообщением на заказ |

Оптовый заказ заводят пустым и десятки минут наполняют позициями вручную
(пример: заказ 1075699397 создан в 08:46, последняя позиция добавлена в
09:14 — всего их 65). По статусу «Новый» такой заказ ушёл бы в чат
**пустым файлом**, поэтому для канала `OPT_CHANNEL` действует свой список
статусов готовности:

```bash
OPT_CHANNEL=ОПТ
OPT_STATES=Моя Доставка      # несколько — через запятую
```

Для маркетплейса статусы прежние — `NOTIFY_STATES`.

Маркетплейсом заказ считается при совпадении канала продаж **или**
контрагента с `KASPI_CHANNEL`: в выгрузке они совпадают у 99 заказов из
100, но полагаться на одно поле рискованно. Снятая галочка приходит из
МойСклад как **отсутствие** атрибута, а не как `false` — это учтено.

### Сводный сборочный лист

Копятся заказы Kaspi в статусах из `NOTIFY_STATES`. Файл уходит, когда
набралось `BATCH_SIZE` заказов **либо** когда самый старый из накопленных
ждёт дольше `BATCH_MAX_WAIT_MINUTES`. Второе условие обязательно: поток
около 50 заказов в сутки, десяток набирается за 2–3 часа, и без таймера
заказ мог бы пролежать до следующего дня.

В файле два листа:

* **«Маршрут сборки»** — все позиции всех заказов в порядке обхода склада,
  чтобы пройти стеллажи один раз. Номер заказа — в последней колонке.
* **«По заказам»** — та же выборка, сгруппированная по заказам: что в
  какой пакет положить и куда смотреть при спорной позиции.

Состав листа — это всегда «что прямо сейчас в нужных статусах». Заказ
собрали и перевели дальше — он сам выпадает из следующего листа, отдельный
учёт не нужен. Уже отправленные заказы помнит `BATCH_STATE_FILE`.

```bash
BATCH_SIZE=10                 # максимум заказов в одном файле
BATCH_MAX_WAIT_MINUTES=60     # сколько ждать наполнения
BATCH_INTERVAL=60             # как часто проверять пул, секунд
```

## Оповещения о новых заказах в чат склада

Бот сам постит новый заказ в закрытый чат сотрудников — тем же форматом.

1. Добавьте бота в чат склада (и дайте право писать сообщения).
2. Отправьте в чате `/chatid` — бот ответит id, у групп он отрицательный.
3. Впишите его в `.env` и перезапустите бота:

```bash
NOTIFY_CHAT_ID=-1001234567890
POLL_INTERVAL=60          # как часто спрашивать МойСклад, секунды
NOTIFY_SINCE=today        # today (по умолчанию) | now | «2026-09-10 00:00:00»
NOTIFY_STATES=            # пусто = все новые; иначе, например: Новый,Подтвержден
```

**Что уходит в чат.** Только заказы, созданные с начала текущего дня
(`NOTIFY_SINCE=today`). Историю бот не выгружает никогда: если он был
выключен неделю, при старте отметка сдвигается на сегодняшнюю полночь, а
не отматывается назад. Нужно ловить только то, что появится после
запуска, — поставьте `NOTIFY_SINCE=now`.

Как это работает: у МойСклад нет пушей без публичного вебхук-адреса,
поэтому бот раз в `POLL_INTERVAL` секунд запрашивает заказы с
`filter=created>=<отметка>`. Отправленные id хранятся в `STATE_FILE`
(`state.json`), поэтому перезапуск не приводит к повторным сообщениям.

**Часовые пояса.** Аккаунт МойСклад заведён по Москве (UTC+3), склад
работает в Алматы (UTC+5) — расхождение два часа. МойСклад отдаёт и
принимает даты в поясе аккаунта, **не указывая смещение** (фильтр вида
`...+0500` API отклоняет с ошибкой 400) и сам пояс через API не сообщает,
поэтому пояса заданы настройками:

```bash
MOYSKLAD_TZ=Europe/Moscow   # в каком поясе аккаунт МойСклад
DISPLAY_TZ=Asia/Almaty      # в каком поясе работает склад
```

Все даты, которые видят люди, переводятся в `DISPLAY_TZ`, а границы для
фильтров API — обратно в `MOYSKLAD_TZ`. Без этого «заказы с начала
текущего дня» смещались бы на два часа: полночь в Алматы — это 22:00
предыдущего дня по Москве. Пояса проверяются тестом и печатаются в лог
при старте. На случай неверной настройки осталась страховка: граница не
поднимается выше момента последнего изменения (но отматывается не больше
суток), а срабатывание пишется в лог предупреждением.

**Доступ.** Как только задан `NOTIFY_CHAT_ID`, бот работает только для
этого чата (плюс для тех, кто перечислен в `ALLOWED_USER_IDS`) — посторонний
в личке получит отказ. То есть состав группы и есть список допущенных
сотрудников: убрали человека из чата — он потерял доступ к заказам.
Открытым для всех бот остаётся, только если не заданы ни `NOTIFY_CHAT_ID`,
ни `ALLOWED_USER_IDS`.

В самом чате бот не встревает в переписку: отвечает на команды и на
сообщение, целиком состоящее из цифр номера заказа.

## Права токена в МойСклад

Учётной записи нужны права на:

* просмотр **Заказов покупателей**;
* просмотр **Складов** (включая ячейки адресного хранения);
* отчёт **Остатки** — краткий отчёт `/report/stock/byslot/current`
  доступен только администратору или сотруднику с правом на Остатки.

## Как это устроено

| Данные | Источник |
|---|---|
| номер, дата, статус, канал продаж | `GET /entity/customerorder?filter=name=…&expand=state,salesChannel,agent,store` |
| позиции, количество, штрихкод | `GET /entity/customerorder/{id}/positions?expand=assortment.uom` (по 100 на страницу) |
| новые заказы для оповещений | `GET /entity/customerorder?filter=created>=…&order=created,asc` |
| адресный склад | `GET /entity/store?filter=name=Склад адрес. хранение` |
| номера ячеек | `GET /entity/store/{id}/slots` (по 1000 на страницу) |
| остаток по ячейкам | `GET /report/stock/byslot/current?filter=storeId=…;assortmentId=…` |

Отчёт по ячейкам возвращает только `slotId`, поэтому справочник ячеек
(`id → номер`) кэшируется на 10 минут, сам склад — на час. `/refresh`
сбрасывает оба кэша. Ответ `429` повторяется с задержкой из заголовка
`X-Lognex-Retry-After`.

Товары, лежащие **вне ячеек**, в отчёт не попадают — такая позиция
покажется как «нет остатка в ячейках».

## Устойчивость к сбоям МойСклад

В логе за четверо суток: 7937 запросов, 7 ответов `503` — примерно один на
тысячу. Это кратковременные сбои сервиса, и обрабатываются они на двух
уровнях:

1. **Повтор запроса.** Коды `429`, `500`, `502`, `503`, `504` и обрывы
   связи повторяются до четырёх раз с нарастающей паузой. У `429` паузу
   подсказывает сам МойСклад заголовком `X-Lognex-Retry-After`. Прочие
   ошибки (`401`, `403`, `404`) поднимаются сразу — повторять их бессмысленно.
2. **Отложенная отправка.** Если отчёт по ячейкам всё же не ответил,
   заказ не уходит в чат без адресов хранения — такая карточка сборщику
   бесполезна. Он откладывается и повторяется на следующем круге опроса
   (до пяти раз), и только потом отправляется с пометкой «Ячейки не
   получены». Отметка времени при этом не двигается, иначе заказ выпал бы
   из следующей выборки и потерялся.

HTML-заглушки, которые МойСклад отдаёт вместо JSON при сбое, заменяются
понятным текстом: вместо `<html>…503 - Service Unavailable…</html>` в чат
попадает «МойСклад 503: сервис временно недоступен».

Документация API: <https://dev.moysklad.ru/doc/api/remap/1.2/>

## Деплой на сервер

Бот разворачивается как systemd-сервис: автозапуск при загрузке сервера,
перезапуск при падении, логи в journald, защита от второго экземпляра
(два процесса на `getUpdates` — это `Conflict` от Telegram).

Всё нужное лежит в [deploy/](deploy/):

| Файл | Назначение |
|---|---|
| `deploy/preflight.sh` | Проверка сервера ДО деплоя: доступность `api.telegram.org` и `api.moysklad.ru`, версия Python, права. Ничего не меняет. |
| `deploy/moysklad-bot.service` | systemd-юнит: пользователь без права входа, `Restart=on-failure`, `ProtectSystem=strict`. |
| `deploy/deploy.sh` | Синхронизирует код на сервер (rsync), ставит venv и зависимости, кладёт юнит, перезапускает сервис. Идемпотентен — повторный запуск обновляет код. |

### Порядок действий

```bash
# 1. Проверка сервера (доступность API — особенно важно, если сервер в РФ:
#    Telegram может быть заблокирован на исходящих)
ssh user@host 'bash -s' < deploy/preflight.sh

# 2. Первый деплой
./deploy/deploy.sh user@host

# 3. Заполнить токены на сервере (деплой сам их не трогает и не перезаписывает)
ssh user@host
sudo nano /opt/moysklad-bot/.env   # TELEGRAM_TOKEN, MOYSKLAD_TOKEN, NOTIFY_CHAT_ID
sudo systemctl restart moysklad-bot

# 4. Обновление кода в дальнейшем — тот же самый deploy.sh
./deploy/deploy.sh user@host
```

`deploy.sh` не трогает на сервере `.env`, `state.json`, `batch_state.json` —
их источник истины сервер, а не эта машина. Первый запуск копирует
`.env.example` как заготовку и явно просит заполнить токены.

Полезные команды на сервере:

```bash
sudo systemctl status moysklad-bot      # жив ли, давно ли перезапускался
sudo journalctl -u moysklad-bot -f      # живой хвост лога
sudo systemctl restart moysklad-bot     # перезапуск после правки .env
```

**Перенос состояния.** Если бот уже работал где-то ещё (например, на этом
Mac) и нужно не рассылать заново уже обработанные заказы — скопируйте
`state.json` и `batch_state.json` на сервер вручную ДО первого запуска
сервиса. Иначе первый запуск начнёт с `NOTIFY_SINCE` (по умолчанию —
начало текущего дня).

## Структура

```

main.py               точка входа
msbot/config.py       настройки из .env
msbot/moysklad.py     клиент JSON API (retry на 429, пагинация)
msbot/orders.py       сборка карточки заказа + кэш склада и ячеек
msbot/formatting.py   текстовая таблица с разбивкой по 4096 символов
msbot/excel.py        выгрузка заказа в .xlsx, настроенный на печать
msbot/imagetable.py   та же таблица картинкой (PNG), если ORDER_FORMAT=image
msbot/delivery.py     единая отправка карточки в выбранном формате
msbot/timezones.py    переводы между поясом аккаунта и поясом склада
msbot/slots.py        разбор имён ячеек, маршрут обхода и приоритет съёма
msbot/bot.py          хендлеры aiogram, белый список пользователей
msbot/notifier.py     опрос смен статуса, отсечка по дню, постинг в чат
msbot/routing.py      разведение заказов: сводный лист / экспресс / поштучно
msbot/batcher.py      накопление заказов Kaspi и отправка сводного листа
diagnose.py           проверка связи: Telegram, МойСклад, карточка заказа
send_order.py         ручная отправка заказа в чат или выгрузка .xlsx на диск
tests/                тесты на подставном API, без сети
```

## Тесты

```bash
cd tests && for t in test_smoke test_client test_handlers test_notifier \
                     test_excel test_timezones test_slots test_batch; do
  ../.venv/bin/python $t.py || break
done
```

Проверить связь и увидеть карточку последнего заказа:

```bash
./.venv/bin/python diagnose.py                       # связь + последний заказ
./.venv/bin/python diagnose.py 1069127266            # конкретный номер
./.venv/bin/python diagnose.py --notify              # что уйдёт в чат, без отправки
./.venv/bin/python send_order.py 1068634272          # отправить заказ в чат вручную
./.venv/bin/python send_order.py --save ./out 1068634272   # сохранить .xlsx на диск
```

Для `ORDER_FORMAT=image` на сервере нужен шрифт с кириллицей:
`apt-get install fonts-dejavu-core`. Для `xlsx` и `text` шрифты не нужны.
